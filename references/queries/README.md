# Where the data comes from

The pipeline starts from one CSV export of the miniJPAS catalogue:

```
data/raw/miniJpas_fluxes_errors_redshifts_full.csv
64,327 rows x 137 columns, 78 MB
sha256 e747b331be4a27657bb2afd98ebdb71dc5fd52d0ead76b0431ac68d082deace5
```

`data/` is git-ignored, so a fresh clone has **no** raw file and every `make`
target that starts from it will stop with `FileNotFoundError`. Get the CSV before
running anything: `references/getting-started.md`, section 2.

## The queries

| File | What it is |
|---|---|
| `minijpas_flux_with_errors_full.txt` | **The query that produced the shipped CSV.** Identical to the first line of the CSV after normalising whitespace (5,936 characters each), so the file on disk and the committed query are the same query. |
| `minijpas_flux_with_errors.txt` | The first draft. Differs from the shipped one in three ways: no `tile_id` / `number` / `ALPHA_J2000` / `DELTA_J2000`, no `angDist`, and an inner `JOIN` instead of `LEFT JOIN` on the SDSS cross-match. Do not use it to reproduce the data. |

Both files are copies of a query typed into the archive's SQL console; neither
is generated by code in this repository, and nothing here executes them.

The archive and its SQL endpoint are **not** named in this repository, because
the export was produced interactively with the author's own credentials. To
regenerate the file you need access to the miniJPAS data release and its
`minijpas` schema, then run the query and save the result as CSV *including the
header*: `dataset.load_raw` detects and skips the `#SELECT ...` line that the
archive prepends, and `dataset.validate_columns` fails loudly if the schema is
not the one the pipeline was written for.

## What the query selects

| Source table | Columns taken |
|---|---|
| `minijpas.FLambdaDualObj` (t1) | `tile_id`, `number`, `ALPHA_J2000`, `DELTA_J2000`, `FLUX_AUTO[band]` and `FLUX_RELERR_AUTO[band]` for all 60 bands, `CLASS_STAR` (aliased `SEtractor`) |
| `minijpas.MagABDualObj` (t3) | `MAG_AUTO[rSDSS]`, `flags[rSDSS]`, `mask_flags[rSDSS]` |
| `minijpas.xmatch_sdss_dr12` (t2) | `class`, `spCl`, `zsp`, `e_zsp`, `f_zsp`, `zph`, `e_zph`, `avg_zph`, `angDist` |

`t1` is joined to `t3` on `(tile_id, number)` and **left**-joined to `t2` on the
same keys, which is why 44,420 of the 64,293 objects have no SDSS match. The
band axis is spelled `minijpas::<band>` in the query and flattened to one column
per band in the CSV, named after the band (`J0450`) with an `e` prefix for the
relative error (`eJ0450`).

Four properties of this export drive the whole pipeline and are measured in
`references/data_dictionary.md`:

- `FLUX_RELERR_AUTO` is a **signed relative** error, not an absolute one.
- `relerr == 0` means *not computed*, not *infinitely precise* (1.009% of pixels).
- 34 `(tile_id, number)` pairs are duplicated, all from the SDSS cross-match.
- `MAGrSDSS` and `angDist` leak label availability and are kept as metadata
  only, never as features.

## Verifying a copy

```bash
sha256sum data/raw/miniJpas_fluxes_errors_redshifts_full.csv
# e747b331be4a27657bb2afd98ebdb71dc5fd52d0ead76b0431ac68d082deace5

head -c 200 data/raw/miniJpas_fluxes_errors_redshifts_full.csv
# #SELECT t1.tile_id as tile_id, t1.number as number, ...

uv run python -c "from jpas_da.dataset import load_raw, validate_columns; \
                  d = load_raw(__import__('pathlib').Path('data/raw/miniJpas_fluxes_errors_redshifts_full.csv')); \
                  validate_columns(d); print(d.shape)"
# (64327, 137)
```

`make data` on this file is deterministic: rebuilding produces an identical
`data/interim/objects.parquet` (checked with `DataFrame.equals` over every column
and row), so the per-object numbers in `references/data_dictionary.md` are
reproducible.
